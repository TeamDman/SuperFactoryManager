# Tunnelled capability after provider changes: incident investigation

Status: active. A cached tunnel-capability defect is independently reproduced on the published release, and a scoped 1.21.1 relay fix is authorized and under test. Neither reporter's exact setup is yet reproduced. Issue: [#620](https://github.com/TeamDman/SuperFactoryManager/issues/620). Updated: 25 September 2026.

## User intent and scope

This incident has higher investigation priority than the feature and infrastructure lanes, but those lanes remain active parallel work. Begin with a 1.19.2 mechanism probe, then test the reporter's actual environment rather than assuming the newest Minecraft line is most relevant. Build a repeatable regression if possible. Create a player-facing troubleshooting guide and preserve the reporter's evidence in a GitHub issue. Do not change production transfer code merely because a cache-lifecycle hypothesis sounds plausible. After the exact-release red tests and source trace, the user authorized a scoped 1.21.1 far-position capability invalidation relay. A `/sfm fix` command remains deferred; any future command must be non-op and affect only SFM-owned caches.

The reporter, TheVoos, says tunnelled SFM blocks connected to a Mekanism fission reactor stop working after each relog until broken and replaced. Environment reported: ATM10 To the Sky 2.0.4, SFM 4.34. A hopper setup in a *separate SFM-only superflat* did not fail. The supplied video shows two adjacent Tunneled Fancy Inventory Cable blocks in the reactor–turbine gap and describes steam travelling to the turbine and condensed water returning to the reactor. The exact port faces, Mekanism jar version, world/server lifecycle and result of SFM's rebuild control remain unknown. [Original Discord message](https://discord.com/channels/967118679370264627/967119184209264790/1552451966779785352).

A second reporter, druidbruce, describes the break-and-re-place symptom in Techopolis 3 on Minecraft 1.21.1, but explicitly not after relog. Their trigger is either side changing state for certain neighboring blocks. One example is placing the tunnel first, then placing a Mekanism machine or using a Mekanism installer on it. The user clarified that installers are items that upgrade a machine to the next factory tier, not blocks. The reporter says both sides recognize the tunnel only after it is replaced. Their exact installer tier, machine, SFM and pack versions, resource and face remain unknown. This is a separate observation that may share a cause, not proof that TheVoos's relog uses the same path.

Later Discord messages raised a chunk-border hypothesis. TheVoos says both affected ports and the tunnel are in one chunk, but the full reactor footprint is not yet known. Druidbruce suspects a maximum-size reactor may cross chunks and reform as chunks load. Burkino reports that one member does the shared multiblock tick while others are effectively no-ops. TheVoos asks whether ticking members in different chunks could explain the failure. The Discord transcript includes an image marker but not its image; the later supplied video shows the local cable gap but no chunk-border overlay, so it does not establish the full multiblock's chunk footprint. The question to test is whole-structure load/reformation and capability invalidation, not simply whether two ticking blocks occupy different chunks.

[CurseForge's pack files](https://www.curseforge.com/minecraft/modpacks/all-the-mods-10-sky/files/all?page=1&pageSize=20&showAlphaFiles=hide) list ATM10 To the Sky 2.0.4 as Minecraft 1.21.1 / NeoForge. The [published SFM 4.34.0 1.21.1 file](https://www.curseforge.com/minecraft/mc-mods/super-factory-manager/files/8370241) corresponds to source tag `4.34.0-1.21.1`; the current 1.21.1 checkout has changed considerably since that tag and must be tested separately. Per-file download counts favor 1.21.1 strongly, but they are not cumulative player distribution or proof of the affected pack's exact SFM jar.

The installed `sfm-propagate-changes.exe curseforge popular sync` and `curseforge project file list` commands need a CurseForge Core API key. The local-only popularity cache did not provide a usable distribution at this checkpoint, so triage used the public CurseForge file pages instead. This does not change dependencies or the game fixture.

The chunk-border lead is a different, unproven transition. At pinned Mekanism commit `710d8675`, [every casing and port checks the structure, while one elected master ticks the shared data](https://github.com/mekanism/Mekanism/blob/710d8675a7858bafed8d52aa1fdb95b756e2d359/src/main/java/mekanism/common/tile/prefab/TileEntityMultiblock.java#L110-L151). [Formation validates every coordinate](https://github.com/mekanism/Mekanism/blob/710d8675a7858bafed8d52aa1fdb95b756e2d359/src/main/java/mekanism/common/lib/multiblock/CuboidStructureValidator.java#L50-L75), and [chunk lookup does not force-load missing chunks](https://github.com/mekanism/Mekanism/blob/710d8675a7858bafed8d52aa1fdb95b756e2d359/src/main/java/mekanism/common/util/WorldUtils.java#L157-L175). SFM's tunnel proxies the far position without forwarding far-side invalidation to consumers bound to the tunnel position. Thus the full reactor crossing chunks could cause a port capability change after reload even when its ports and tunnel share one chunk. The source does not prove that this happened to TheVoos, that it persists after all chunks load, or that the elected master's chunk alone determines the outcome. SFM's exact-tag `dependencies.gradle:56-57` and lockfile include only Mekanism core and API, while reactor classes are in Mekanism's separate Generators source set. Some steam reaching the turbine or some water moving back can coexist with net water loss. The next safe observation is a before/after comparison of the reactor's heating rate and coolant delta against the turbine's actual flow and maximum water output, plus a fixed view of the full multiblock with chunk borders; keep the failsafe enabled.

## Operational boundary and next checkpoint
