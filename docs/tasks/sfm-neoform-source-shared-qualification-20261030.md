The existing branch 1.21.0 source JAR is 9,272,675 bytes, SHA-256 `72fec3820feedcce59e32b22420f8b7636202cd0023e76f3b4f5f7afdb0f6d78`. Two already published, independently verified local NeoForm dependency entries for dev 1.21.0 each have 7,220 unique ZIP entries and 9,259,327 bytes. Their JAR SHA-256 values are `795a21af76a0834d062c5569f0514f407e3c6a08d9b5d6ba92227955fe9a3990` and `824b5a4c75357c25581229a64ef3ae3e66628c8d672e26164563a92ad2322312`. Every corresponding entry payload is identical between those two; only the container differs. Their local dependency keys differ only in the host implementation identity, not the frozen source lock or ordered producer receipt. This is a narrow observation, not proof of universal NeoForm output determinism.

The historical branch JAR has the same 7,220 entry names but differs in 4,436 payloads from the catalog producer sample (for example `com/mojang/blaze3d/audio/Channel.java`). Its source tree must not be copied or accepted as the current catalog output. A diagnostic name/length/entry-payload digest is identical for the two catalog samples (`5b530469d04fd09a133564edc9383ca478356a9117d9e9b9fbf45354d7ba35ec`) and differs for the branch sample (`eb2199caacfb610748e9d98e00e791fc55cb289cd5d892c23098502119535f6f`). This diagnostic digest is not a lock format or admission check.

## M3.8 changed-class runtime witness design

The existing `runtime_session.rs` controlled fixture changes `classes/Main.class` bytes between two snapshots while preserving options/world marker/console bytes; that is not a live JVM witness. The two live 1.19.2 tests in the cutover packet changed only the GameTest selector, not class bytes. A bounded next witness can use task-owned fixture classes and two distinct generated snapshot receipts for the **same projection identity**, then launch a short task-owned JVM against each prepared session's private class root while the first session remains held. It should assert the process-observed class marker changes, the second snapshot identity differs, and saved options/world marker and first session bytes remain unchanged; no user projection sources or worlds need mutation. This proves the runtime-session handoff with live class loading, not Minecraft GameTest semantics. If the acceptance criterion specifically requires a Minecraft server executing changed SFM classes, a separate reviewed test-only build-input mechanism is needed; the fixture must not silently stand in for that wider claim.
