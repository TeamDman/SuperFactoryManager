## Approved adapter result

`build/features/locked_dependency_projection/26.1.2/settings.gradle` now has opt-in `-PsfmUseLockedMinecraftMetadata=true`, requires the existing guarded repository toolchain mode and `--offline`, authenticates the selected SFM lock and version bytes, refuses conflicting Gradle cache files, and publishes only the two expected metadata files under the selected Gradle home with an owned lock and atomic writes. Dev and 4.35 extended 26.1.2 generated projections pass strict source check; plain 4.34.0 source check passes with no adapter feature.

In a fresh isolated Gradle home, offline `help` ran the adapter and retained exact selected 26.1.2 version SHA-256 `1AEE43F4486C9B6E0E03F7E0B0D04F7994E27DE40BD1F7496AB6201363AD7B09`, then failed because Gradle itself has not cached project module metadata (`at.yawk.lz4`, `azure-json`, and others) for offline resolution. A task-owned home with the local Maven bootstrap resolved those modules in online mode, but NeoGradle still attempted the mutable v1 URL; a disabled external proxy made that fail. The adapter now rejects online mode *before* publication, and an offline conflict test rejects an existing different launcher file without changing either destination. These are bounded guarded-reader results, **not a successful cold `help`, `jar`, or runtime test**. Logs are `action-services-evidence/m22-adapter-dev2612-{offline-help,online-reject,conflict-reject,proxy7-help}-20261030.log`.

## Fresh offline module closure after adapter selection

The fresh offline Gradle home reported 80 distinct unresolved module coordinates. Seventy-seven already have POM or Gradle-module metadata in the checked 110-file project manifest; three (jsr305 3.0.2, listenablefuture 9999.0-empty-to-avoid-conflict-with-guava, and jopt-simple 5.0.4) have direct frozen JAR records but no project-manifest metadata. Across the 80, 14 have both a direct SFM artifact and a nested library record in the authenticated 26.1.2 version JSON, 37 are nested-library-only, 27 are direct-lock-only, and two are neither. All 78 JARs in the direct/nested groups exist at their selected SFM cache paths. The other two JARs are net.neoforged:mergetool:2.0.7 (required by checked NeoForge 26.1.2.72 and NeoForm 26.1.2-1 module metadata) and org.jetbrains:annotations:26.0.2-1 (required by checked NeoGradle 7.1.27 metadata). Their official JAR bytes were fetched into task evidence only and verified against the SHA-256 and sizes in the already checked module metadata: mergetool 28,166 bytes/aca2de408721b77c664334030cf7d2013a80f4871e025337621d292e0e5ae265; annotations 31,170 bytes/2037be378980d3ba9333e97955f3b2cde392aa124d04ca73ce2eee6657199297. They have not been admitted to the checked-in manifest or shared Gradle repository.

The settings bootstrap validates and publishes all 110 checked files into its local Maven repository, but the project repository currently exposes only complete NeoForge, NeoForm and JST modules from that repository. Gradle offline therefore does not discover the other 77 metadata records; simply widening the repository filter would strand modules whose JAR bytes are in different SFM cache layouts. A complete checked module route must join each metadata record with its required variant JAR from the authenticated version JSON, direct frozen lock, or separately verified NeoGradle/NeoForm graph, then test Gradle's artifact origin and offline resolution. This is a real remaining closure, not permission to copy an unverified warm Gradle cache or silently admit the two missing JARs. For example, the selected version JSON pins at.yawk.lz4:lz4-java:1.10.1 to SHA-1 f541d7f910fe3d76f38f799c507c48cc81b12ecb and 910,232 bytes, and com.azure:azure-json:1.4.0 to SHA-1 fcc1d354dbc3e0300e5276b1bf124d0247799cd8 and 325,945 bytes. No new JAR admission or repository broadening was performed in this checkpoint.

## Recommended migration decision, not yet authorized

Prefer one reviewed **exact-snapshot alignment** for the six NeoGradle targets over growing a permanent metadata bridge. Keep plain 4.34.0/4.35.0 historical locks and manifests byte-for-byte. The exact core key set is `sfm-4.34.0-extended/mc-V`, `sfm-4.35.0-extended/mc-V`, and `sfm-dev/mc-V` for each of the six V values in the table (18 keys). The locked-dependency feature also feeds `sfm-4.34.0-issue610-portable/mc-V` and `sfm-4.35.0-issue610-portable/mc-V` for all six V, plus `sfm-4.34.0-issue610-visual/mc-1.21.1`, `sfm-4.35.0-issue610-visual/mc-1.21.1`, `sfm-4.34.0-issue610/mc-1.21.1`, and `sfm-4.35.0-issue610/mc-1.21.1` (16 additional keys). Thus seven feature-lock inputs feed 34 generated projection locks, not just the 18 core keys. Before a lock change:

1. Pin an exact authenticated v1 launcher snapshot or replace discovery with six explicit content-addressed version URLs. Do not let a moving global manifest select a different URL after review. Record the official URL, full digest, selected timestamp and exact mapping to the six payloads. The four fetched index JSONs and the six authenticated retained version JSONs are proposal evidence, not yet admitted SFM lock inputs.
2. Change `build/lockfiles/V/schema-4.json` for each of the six V targets, plus `build/lockfiles/1.21.0/schema-4-dev-catalog-source.json` for the developer-only catalog source route: each direct version URL and BLAKE3-20 hash becomes the table's v1 payload, with its nested asset-index URL/SHA-1/size and object hashes verified. The 1.21.0 dev-specific lock currently has the same old direct version pin but different source-provider content; retain that difference. These seven inputs feed 18 core extended/dev projections and 16 issue-610 variants; changing only dev would require a new selector or recipe split. `project-inputs.json` selects `schema-2.json` when `locked_dependency_projection` is absent, so plain 4.34.0/4.35.0 release outputs can remain byte-identical if their generation checks pass. Preserve old pins and receipts as historical evidence. The currently pinned v2 manifest does not select these v1 URLs, so changing only direct artifact records would make future regeneration disagree; a reviewed source-discovery recipe transition is required.
3. Design a version/recipe-keyed index cache path and compatible version-metadata path. The current named paths (`assets/indexes/{id}.json`, `versions/{mc}/version.json`) already contain old checked bytes; `acquire_named_frozen_download` verifies existing bytes and fails on mismatch. Do not overwrite them or erase existing receipts to force the new pins. Recheck source-index, compile, launch and runtime receipts whose version-parent or asset-index identities change; preserve all old worlds/options and plain-release fidelity.
4. Separately close cold Gradle resolution. Its own module metadata is unavailable in a fresh `--offline` home, while online NeoGradle refreshes the mutable global manifest. Choose a checked bootstrap/reader contract for the pinned snapshot, and prove fresh-home `help`/JAR plus repeat reuse without arbitrary network substitution. Native lock alignment alone does not close this gate.

Expected benefit is consistent version/asset selection across SFM native and NeoGradle's selected snapshot, with content-addressed asset reuse across projections. Costs include up to the measured 92.7 MB distinct new object payloads before existing-cache reuse, new receipt/cache identities, asset acquisition, and full applicable build/client/GameTest requalification. The actual allocated growth and full cold-build outcome remain unmeasured. No lock migration, old-cache retirement, broad asset fetch, or plain-release rewrite is authorized by this investigation.
