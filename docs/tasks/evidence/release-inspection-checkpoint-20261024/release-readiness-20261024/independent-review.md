# Projection release readiness — independent source review

Reviewed `/workspace/SuperFactoryManager` at `704ddb5485173093cad42c07975fa5aabfc247ed` on 2026-10-24. Repository status was clean. This was a read-only source/test audit: no builds, tests, publish commands, credentials reads, network calls, settings changes, pushes or merges were performed. This report is the only new reviewer artifact.

**Conclusion:** JAR building has named-projection entry points, but the live CurseForge and Modrinth release commands have not been connected to those projections or their verified artifact provenance. Existing `source legacy` release-package and provider-request work offers useful verification components, not an operational named-projection publisher.

All source references below are relative to `platform/cli/sfm-propagate-changes/src/` unless otherwise stated.

## Readiness blockers and concrete gaps

1. **High — live publishing still selects the old roots and worktrees.** `cli/curseforge/release/curseforge_release_now_cli.rs:79–92` and `cli/modrinth/modrinth_release_now_cli.rs:73–82` read the repository-level `platform/minecraft/gradle.properties`, shared JAR directory and branch selection. `branch_targets/minecraft_version_selection.rs:12–19` explicitly derives versions from matching worktrees. The root properties currently say `mod_version=4.34.0` (line 45), while the ten `platform/minecraft/projections/sfm-4.35.0/*/gradle.properties` say `4.35.0`. Consequently selecting a branch does not select that branch's named 4.35.0 projection or its release version. The required bridge is explicit catalog projection selection and verified release artifact/version/changelog inputs.

2. **High — artifact discovery is incompatible with ordinary native build output and does not establish provenance.** Both live collectors require filenames ending exactly `-<mod_version>.jar` (`cli/curseforge/curseforge_cli.rs:549–600`, `cli/modrinth/modrinth_cli.rs:396–446`). A `-4.35.0-rust.jar` output is excluded. The old `cli/jar/jar_collect_cli.rs:20–86` walks worktrees and their `platform/minecraft/build/libs`, then copies/renames to the shared directory; it does not collect the named projection roots. Renaming/copying alone would not bind a selected JAR to its projection, source commit, recipe or reviewed hash.

3. **High — partial or duplicate release sets can be accepted.** `cli/curseforge/curseforge_cli.rs:257–277` and `cli/modrinth/modrinth_cli.rs:298–318` retain matching filenames and only require a nonempty result. If two Minecraft versions were selected but one matching JAR exists, selection succeeds; two different matching filenames for the same Minecraft version can both survive. This is source-evidenced behavior, not a newly executed reproduction. A future adapter should require exact target-set coverage and one verified artifact per target. Add deterministic missing-target, duplicate-target and extra-target cases before relying on matrix publication.

4. **High — the live upload is not bound to previously reviewed artifact bytes.** CurseForge attaches the JAR path at upload time (`cli/curseforge/curseforge_cli.rs:443–466`). Modrinth does own the bytes before transport, but reads them in `prepare_project_version` without an expected reviewed digest (`cli/modrinth/modrinth_cli.rs:113–142`), after the live command's plan/confirmation. Thus replacement between review and preparation is not rejected. Its existing ownership test proves that replacement *after* preparation cannot change the uploaded bytes; it does not prove that those bytes match the reviewed projection build. Reuse the verified-package hash and bounded owned-read approach when implementing the bridge.

5. **Medium — a Linux unit-test expectation is stale.** `cli/source/core_project_cli.rs:527–546` expects matching NeoForm recipe preflight success only under `cfg!(windows)`. The production gate in `jar_build/engine_named_nfrt_compile.rs:61–78` accepts Windows or Linux. On Linux, the matching-recipe assertions therefore disagree with the production implementation. This is a directly established source mismatch; the test was not run in this audit. Update the assertions to the intended supported-platform gate and run the relevant native tests.

## Adapted components and their limits

- `cli/jar/jar_build_options_args.rs:16–19` exposes projection selection; `cli/jar/jar_build_cli.rs:16–32` routes it to the native build engine and supports a create-only output name. `cli/source/core_project_cli.rs:248–249` dispatches native JAR production; its native compile path loads the catalog entry and preflights the exact target/recipe (`:279–288`). These are real migration adaptations. This audit did not execute a matrix build or establish ten-target release readiness.
- `platform/minecraft/projections.json:6–15` declares exactly ten 4.35.0 release projections. The legacy candidate fixtures also include ten targets, including `26.1.2`; `1.21.0` correctly maps to Minecraft `1.21`. There is no basis for claiming that the older provider plan excludes 26.1.2.
- Live loader metadata remains inferred from Minecraft version: Forge through 1.20, Forge plus NeoForge for 1.20.1, NeoForge thereafter (`cli/curseforge/curseforge_cli.rs:711–724`, `cli/modrinth/modrinth_cli.rs:321–333`). CurseForge's Java mapping includes Java 25 for 26.x (`:726–735`). These mappings cover the existing matrix but are not checked against the live selected JAR's typed loader/JDK provenance. The verified provider plan does cross-check typed values and requires an explicit Modrinth 1.20.1 policy (`cli/source/release_provider_plan_cli.rs:293–322,483–517`).
- `source legacy release-package` verifies a frozen inventory against an exact candidate lock before copying (`cli/source/release_package_cli.rs:125–150`). Its contract is the historical preset/source-manifest model: `source_projection/candidate_lock.rs:118–120` requires `released-<mod_version>`, and `:230–257` verifies the complete preset matrix and typed target metadata. It is not a direct `--projection sfm-4.35.0/*` publishing interface. Do not assume an adapter exists merely because the target counts agree.
- Provider planning explicitly leaves current HEAD, tag object, remote project ownership and CurseForge numeric game-version IDs unchecked (`cli/source/release_provider_plan_cli.rs:397–418`). The target-plan layer additionally verifies local HEAD, source tree, selected root provenance, commit tree, exact target tag and JAR digest (`cli/source/release_target_plan_cli.rs:102–140`). It still expressly does not check remote tags or authorize publication.
- Despite its name, `source legacy release-modrinth` is read-only request preparation. It bounds the selected JAR to 64 MiB, verifies its hash, constructs the shared owned upload object, then drops it; no HTTP client or send occurs (`cli/source/release_modrinth_cli.rs:27–28,62–97`). This is deliberate and accurately reported, not a hidden publishing implementation. CurseForge's provider plan similarly leaves remote ID resolution to a later stage.
