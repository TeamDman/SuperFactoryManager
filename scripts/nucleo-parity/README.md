# Java Nucleo matcher: parity contract and integration handoff

This is an optional, dependency-free Java 17 port of Nucleo's **literal fuzzy
matcher**, with a standalone Rust differential oracle. No existing SFM UI or
ranking is switched over. The authored Java lives in
`platform/minecraft/core-liquid-template/src/main/java/ca/teamdman/sfm/client/search/nucleo/`.
These pure shared sources need no version-specific Liquid rule; normal source
inventory discovery includes them. Release projections are not regenerated by
this change. `docs/source-projection-contributor-guide.md` describes that workflow.

## Exact reference and supported slice

* Official source: <https://github.com/helix-editor/nucleo>
* Pinned commit: `8c16d47cdfa9607d3e44df5f81c635c6f43c65ee`
* Matcher crate: `nucleo-matcher` 0.3.1. Relevant files: `lib.rs`,
  `fuzzy_optimal.rs`, `fuzzy_greedy.rs`, `prefilter.rs`, `score.rs`, `matrix.rs`,
  `exact.rs` (single-character shortcut), `config.rs`, `chars.rs`,
  `chars/{normalize,case_fold}.rs`, and literal `pattern::Atom::new` preparation.
* Oracle compiler: `rustc 1.99.1 (58cf8f9c3 2026-10-13)`, release arithmetic,
  x86_64 Linux. Frozen character classification: Rust Unicode 17.0.0.
  Nucleo's case-fold table is Unicode 15.0.0. Java's Unicode implementation is
  deliberately not used for classification, case folding or normalization.
* **Parity profile:** `unicode-casefold` and `unicode-normalization` enabled;
  `unicode-segmentation` disabled. The reference operation is
  `Atom::new(query, case, normalization, AtomKind::Fuzzy, false).indices(...)`
  and `.score(...)`, with candidates constructed by `Utf32Str::new`.
* No parsed `Pattern` syntax, multiple atoms, negation, escaping, substring,
  prefix, postfix or exact-mode API. Query punctuation and whitespace are
  literal. No trimming, word splitting, or spelling/edit-distance tolerance.
* No claim of Helix/Nucleo frontend, concurrent injection, incremental matching,
  worker scheduling, grapheme highlighting, or end-to-end UI parity. No claim of
  equal performance or allocation behavior. The Java DP uses rolling score rows
  and a bounded byte backtracking matrix, without upstream SIMD prefilters.

| Setting | Java behavior and Rust reference |
| --- | --- |
| `CaseMode.RESPECT` | Preserve query case; `CaseMatching::Respect` |
| `CaseMode.IGNORE` | Simple one-codepoint case folding; `CaseMatching::Ignore` |
| `CaseMode.SMART` (default) | Ignore case only when the original query contains no key in Nucleo's fold table; same as `CaseMatching::Smart` (this is more precise than JDK `isUpperCase`) |
| `Normalization.NEVER` | `Normalization::Never` |
| `Normalization.SMART` (default) | Normalize candidate Latin variants only if no query character, after IGNORE folding if requested, changes under Nucleo's normalization table |
| `Boundaries.DEFAULT` (default) | `Config::DEFAULT` boundaries: `/,:;\|`, whitespace bonus 10, delimiter bonus 9, initial whitespace |
| `Boundaries.PATHS` | Unix **`set_match_paths()`**, `/` and `:` delimiters, whitespace bonus 8, initial delimiter. This is intentionally distinct from upstream `match_paths()` (which omits `:`). Windows-dependent backslash behavior is not exposed |
| `preferPrefix` (default false) | `Config.prefer_prefix`; preserves shortcut-specific behavior, including no bonus in the single-character fast path |

Normalization is Nucleo's limited, one-codepoint Latin-to-ASCII table, **not
NFC/NFD/NFKC, general accent removal or locale-dependent lowercasing**. For
example `e` can match `é` in SMART mode, but `é` does not match `e`; `ss` does not
match `ß`. Combining marks and ZWJ emoji components remain separate codepoints.

Inputs must be well-formed UTF-16. Unpaired surrogates throw
`IllegalArgumentException`; Rust strings cannot represent them either. Queries
are limited to 2,048 codepoints; candidates to 65,535 codepoints. Oversized input
throws rather than silently truncating or inventing an approximate score. These
are deliberately narrower than upstream's public 32-bit length limit. At
internal matrix-size boundaries, Java uses the same release-mode greedy fallback
decision (102,400 cells and the 133,120-byte slab layout) as the pinned matcher.
Score arithmetic preserves upstream's u16 prefix-penalty wrapping on long
candidates. Long strings are for contract tests, not a recommended UI workload.

### Results, ties, and highlight mapping

`NucleoMatcher.match` returns `null` for absent matches, otherwise an immutable
`Match`. Scores are integers, higher is better; zero is a valid score.
`score(Candidate)` returns `-1` for absent matches and avoids highlight work.
Empty query matches every candidate with score 0 and no positions. Candidates
can be precomputed once per eligible-list snapshot; they are immutable and safe
to share. A matcher reuses mutable scratch arrays and must belong to one worker.

`Match.codePointPositions()` contains the actual indices returned by Rust, in
ascending order. `utf16Spans()` maps them into the **original candidate string**,
merging adjacent codepoints into half-open `[start,end)` ranges. A supplementary
character occupies one match index and two UTF-16 units. For query `😀x` against
`a😀_x`, positions are `[1,3]`, spans `[1,3),[4,5)`. These are not pixel offsets,
UTF-8 offsets, grapheme indices, or ranges in an insertion string/other field.

Internal ties are deliberately preserved: the optimal DP selects the last
equally scored endpoint; consecutive and gap ties take the skip branch;
single-character fast paths select the first strictly best occurrence. Results
cannot be reproduced by finding a convenient subsequence after scoring.

`NucleoSearch` accepts an already eligible list of `Entry<T>` values. It never
discovers candidates or rewrites payloads. It ranks by caller-defined priority
(lower first), then score descending, then original input index ascending. With
all priorities equal this matches Rust `Atom::match_list` stable ordering;
priority tiers are an **SFM adapter extension**, not upstream matcher behavior.
Duplicate strings retain separate payload identities. Empty query retains input
order within each priority. `limit=0` returns no results; negative limit throws.
Only the top K receive highlight computation. A `BooleanSupplier` and thread
interruption provide cancellation between candidates and before/after sorting
and highlighting. Cancellation throws `CancellationException`, never returns
partial results. A single candidate match is not interruptible mid-DP; both
input and DP sizes are bounded.

### Pinned upstream quirks retained

Parity includes behavior that may be surprising. The Unicode one-character
shortcut carries the class of the previous **matching** character, not every
preceding character. With IGNORE + NEVER, lower-case fold keys such as `µ`, `ſ`
and final sigma can pass the prefilter but fail class-sensitive normalization;
the Unicode single-character shortcut can return `Some(0)` with the first
prefilter index. A related exact-window path can return fewer indices than query
codepoints. Java reproduces the returned Rust score and positions instead of
inventing highlight positions. Prefer the default SMART normalization for normal
ID matching. These quirks should be reviewed before using NEVER on arbitrary
Unicode display labels. Any future upstream correction needs a new pin and
explicit contract/test update.

## Reproduce without installs

Required existing tools: Python 3, Git, JDK 17+ (compilation uses `--release 17`),
the exact Rust compiler above, Cargo, and cached crates `memchr 2.7.6` and
`unicode-segmentation 1.12.0`. The latter is only for default-feature upstream
tests. Their checksums are in this directory's `Cargo.lock`. This independent
oracle lock does not change SFM's dependency graph. No Java runtime dependency
is added. The runner uses `--offline --locked` throughout and never downloads or
installs anything. Missing tools/cache entries are a concrete prerequisite to
resolve explicitly; do not remove offline mode or substitute versions silently.

The source clone was explicitly authorized for this task. For an existing clean
clone at the pin:

```sh
source /workspace/.sfm-env/env.sh
python3 scripts/nucleo-parity/run.py \
  --upstream /workspace/reference-nucleo \
  --build-dir /workspace/nucleo-parity-verification \
  --benchmarks
```

On another machine, set PATH/JAVA_HOME/CARGO_HOME for its already installed
tools; the environment file is specific to this cloud workspace. Obtain the
official source revision through the user's approved source-acquisition path.
The script checks the exact commit and absence of tracked matcher changes, uses
the unchanged upstream Rust library source directly, regenerates and byte-checks
Java Unicode tables, compiles the Java core, runs behavioral checks, compares
real oracle scores/positions/ordering, and optionally benchmarks sequentially.
It captures source hashes and SFM commit/dirty status before running, rejects
input/checkout changes during the run, rechecks the upstream pin afterward, and
records that unchanged identity in `receipt.json`. Provenance, output-count and
table checks remain active under `PYTHONOPTIMIZE`/`python -O`.

`comparison.json` separates official source input pairs, targeted cases,
exhaustive small-alphabet cases, deterministic random cases, broad Unicode scalar
sampling, boundary lengths, and ordered-list comparisons. The official input
pairs are extracted from pinned `matcher/src/tests.rs` and exercised under all
24 supported settings. This is distinct from executing upstream's own test
assertions. Both are done. Default-feature upstream tests run separately; the
codepoint-feature test run explicitly skips the one unconditional grapheme
truncation test because its premise is outside this contract. Earlier running
that test without segmentation produced the expected CRLF mismatch; it was not
counted as a passing test or patched away.

The extended review suite enumerates all 1,454 folding and 706 normalization
entries in both directions and in competing-occurrence contexts. Adversarial
slab/cell-limit cases make optimal and greedy paths choose different matches,
so a wrong threshold cannot hide behind a unique alignment. It covers both
prefix-penalty wrap points, maximum-length supplementary queries/candidates,
and deterministic endpoint ties. Returned UTF-16 ranges are compared exactly
against independently constructed merged `offsetByCodePoints` ranges; a harness
self-check also rejects split-surrogate and other malformed ranges.

`CoreChecks` additionally tests UTF-16 mapping, malformed/oversized input,
payload identity, priority ordering, top-K equality with full sorting,
cancellation/interruption, extreme priority integers, shared snapshots on two
workers, cross-thread cancellation and a stale-generation publication model. These
checks do not simulate Minecraft rendering or Brigadier/ANTLR execution.
The ordinary repository test class is `NucleoMatcherTests`:

```sh
sfm-propagate-changes test run --projection sfm-dev/mc-1.19.2 \
  --filter NucleoMatcherTests --repo-root . \
  --java-home /workspace/.sfm-env/jdk17
```

## Three integration touchpoints (UI owners retain control)

**SFML autocomplete.** `SFMLIntellisense.getSuggestions` uses ANTLR completion
rules and the current caret/context/intellisense level. Resource actions are
enumerated only for `RULE_resourceId`, with game-loaded/resource-intellisense
gates, from each applicable `ResourceType.getItems()`. Preserve all these gates.
`SuggestedResourceIntellisenseAction` stores the resource type, item and rendered
condensed resource ID; `perform(context)` controls word replacement and the
trailing space. Keep that action object as `Entry.value`. Match the exact
`getComponent().getString()` displayed to the user; apply its own UTF-16 spans to
that same text. Do not derive insertion text from a normalized match.

`SFMTextEditScreenV1` currently gathers suggestions, then sets the PickList query
to the current word; `PickList.sortItems` applies Jaro–Winkler from vendored
Simmetrics, with a separate blank-query keyword preference. That policy ranks
even non-subsequence suggestions. Nucleo filtering would therefore be an
observable behavior change, not a drop-in equivalent. An opt-in ID-ranking
experiment should keep parser/token/label candidates and blank-query keyword
priority, precompute a registry candidate snapshot on the thread allowed to
read registries/components, and run top-K scoring on a bounded executor. Keep
the existing insertion objects and selection semantics. Reuse snapshots until
registry/context identity changes, rather than enumerating/preparing 100K rows
per keystroke. The editor/modal task owns widget changes.

```java
var entries = eligibleActions.stream()
    .map(action -> new NucleoSearch.Entry<>(action, action.getComponent().getString()))
    .toList();
var snapshot = new NucleoSearch<>(entries);
// On a worker, with an immutable text/context snapshot and captured generation:
var ranked = snapshot.search(query, NucleoMatcher.Options.DEFAULT, 50,
    () -> currentGeneration.get() != capturedGeneration);
// On the UI thread, recheck generation, document revision, caret, active surface,
// and eligible-snapshot identity before applying ranked rows. Then retain each
// result.entry().value() for activation and its match().utf16Spans() for drawing.
```

Cancel/supersede old work on every relevant change and on closing the surface.
Cancellation alone cannot prevent a completed old result arriving after a newer
request; the UI publication check is required. Empty query can use the existing
priority list without a background full scan. This package neither creates an
executor nor owns generation counters and has no Minecraft frame-time evidence.

**Command palette.** `SFMClientActionCommandTree` has availability checks,
Brigadier ranges/frontiers, choice surfaces, exact action-ID preference, history
recency boosts, contextual continuations, kind/command tie order, deduplication,
usage hints and limits. `actionScore` searches ID/path/title/description;
`choiceScore` adds choice text. `SFMCommandPaletteScreen.refreshSuggestions`
already clears stale interactive rows and checks active screen + suggestion
revision on the Minecraft thread before applying a result. Preserve all of
these. Keep eligibility and specialized `argumentCandidates` providers as
owners; do not fuzzy-search arbitrary registry arguments or bypass `canUse`.

The old score is a lower-is-better float with a 0.65 threshold and additive
history adjustments. Nucleo's score is a higher-is-better, length-dependent
integer and is not numerically interchangeable. Evaluate it within the existing
semantic groups or as a separate policy input; explicitly calibrate exact-ID,
history and continuation precedence. `Entry.priority` demonstrates preservation
of a chosen tier, not reproduction of the entire current palette policy.
Retain canonical command ties by preordering entries when required. When several
metadata fields compete, retain the winning field; only highlight a field that
was actually matched (ID positions do not index a title). Do not sum unrelated
field scores or transplant one field's positions. Existing palette policies
and end-to-end candidate/insertion tests must pass before activating an option.

**Explorer.** Its existing literal/regex/legacy-fuzzy options, whole-word logic,
limits, hierarchy ordering, traversal and highlight toggle belong to the
Explorer task. A Nucleo option can use `match != null` for eligibility and
`utf16Spans` for highlights into the displayed basename/path field, preserving
hierarchy ordering unless an explicit relevance-sort mode is requested. Do not
replace `SFMTextMatcher` literal behavior or reinterpret its 0.65 edit-distance
threshold. Whole-word matching and matching multiple fields require explicit
consumer policy; they are not implemented by this matcher. No Explorer files
are changed here.

## Benchmark interpretation

The fixtures contain **generated registry-shaped IDs**, not modpack names and
not captured loaded-game registry data. No suitable captured registry snapshot
was found in the inspected source/test/generated resources. Namespaces, material
names, underscores, multi-part IDs and numbered variants provide reproducible
loads of 1K, 10K, 50K and 100K candidates. They do not establish a real modpack's
candidate distribution or relevance quality.

The benchmark records preparation separately, first invocation, 6 warmups,
21 measured samples, p50/p95 and Java thread allocation. Java score-only and
top-50-with-highlights are separate from Rust score-only; all 32 score-pass
checksums must agree. Runtime files include full CSVs and preparation/cancellation
notes. It is a single-process descriptive benchmark, not JMH, and includes JVM
warmup/GC/shared-host noise. It does not benchmark the old Simmetrics comparator,
registry extraction, UI rendering, frame scheduling, executor contention or
keypress-to-display latency. Cold table initialization and snapshot preparation
must not block the render thread. Fast warm measurements alone do not justify a
synchronous 100K-candidate UI operation. Use a loaded modpack snapshot and an
opt-in UI test before deciding whether to replace existing ranking.
