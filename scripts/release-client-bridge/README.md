# Isolated Forge and NeoForge production client bridge

This is a test-only, file-driven witness for an **unchanged** SFM production JAR. It is outside `platform/minecraft`, the source projection inputs and outputs, and the release build. It is not part of SFM. The runner uses cached Minecraft, loader libraries, LWJGL and assets; it does not use Gradle or download anything. The launcher cache is read-only. The default `-MinecraftVersion 1.19.2` pins Forge 43.4.0 and asset index `1.19`. `-MinecraftVersion 1.19.4` pins Forge 45.0.9 and asset index `3`. `-MinecraftVersion 1.20` pins Forge 46.0.10 and asset index `5`. `-MinecraftVersion 1.20.1` uses the exact transitional NeoForge `net.neoforged:forge:1.20.1-47.1.65` loader and asset index `5`. These four targets use JDK 17 and LWJGL 3.3.1. The 1.20.2 target pins NeoForge 20.2.86, JBR 17, LWJGL 3.3.1 and asset index `8`, with its own bridge source and pack metadata. The 1.21.0 target pins NeoForge 21.0.143, JBR 21, LWJGL 3.3.3 and asset index `17`, with a separate bridge source and pack metadata. The 1.21.1 target pins NeoForge 21.1.206, JDK 21, LWJGL 3.3.3 and asset index `17`; it has its own Mojmap/NeoForge bridge Java source and pack metadata. The 26.1.2 target pins NeoForge 26.1.2.72, JBR 25.0.3, LWJGL 3.4.1 and asset index `30`, with a separate bridge source for its changed client API.

Call `Run-ReleaseClientBridge.ps1` with `-SfmJar`, `-ExpectedSha256`, `-PrismRoot`, `-JavaHome`, and a **new, separate** `-RunRoot`, plus `-MinecraftVersion` for a non-default target. Never pass a live game directory as the run root. The runner checks the cached launch graph before creating the run root, copies only the SFM JAR into that root, builds this tiny Forge bridge from source, starts one isolated client, and stops only the owned Java PID on timeout. For 1.20 it seeds only that scratch game's `options.txt` to skip first-run accessibility onboarding and focus pause. It retains `launch.args`, stdout/stderr, game logs, and any result or screenshot. A missing bridge result must be classified from the log stage, not treated as an SFM failure. Forge itself may make a version-check request; the runner never downloads dependencies or artifacts.

The default `-CaptureMode title` waits for 90 rendered title-screen frames so that the logo and menu widgets have appeared, captures an in-game screenshot through Minecraft's screenshot API, then exits. It does not enter a save or send user input. A title frame is a minimal visible-client startup smoke, **not** world render, GameTest, gameplay, or full release-preset parity. The direct bootstrap classpath is reconstructed from the installer `version.json` plus cached launcher manifests; it is not an ordinary Prism launch.

`-CaptureMode world` creates one new flat integrated-server save named from the run ID inside that run's scratch `game/saves`. The bridge refuses an existing save or a game directory other than its own scratch directory. It waits for the server and client player, places the production `sfm:manager` block on the server thread, verifies that the client received that block and that the player's ray hits it, then captures a screenshot after at least 30 world-render events with the block still targeted (`AFTER_PARTICLES` on earlier bridges, `AfterLevel` on 26.1.2). No keyboard or mouse input is sent, and no user game directory is opened. The runner requires the mode-specific result schema and a 1024×768 PNG. The screenshot must also be visually inspected: a render-stage callback alone cannot prove that the block's model was visible.

Status: separate hidden-window runs of the unchanged official 4.34.0 and fresh projected 4.34.0 production JARs both reached a fully drawn 1024×768 title screen under exact Forge 43.4.0. The bridge reported success after 90 title frames, and the runner verified each PNG and its original JAR hash. The screenshots differ in the normal rotating splash text; both display the same menu controls and four loaded mods. Offline profile-key and cached-JAR compiler-close diagnostics occurred in both runs without preventing the witness. This establishes only a bounded client startup/rendering comparison, not world or gameplay compatibility.

The same two unchanged JARs also passed separate `world` runs in new scratch roots: both produced a 1024×768 view of the manager block after server placement, client replication, ray targeting, and world rendering. Their animated manager side textures need not produce byte-identical screenshots. Both emitted the same offline profile-key diagnostic and a nonblocking `sfm:blocks/buffer` loot-table parse error. These are bounded client-world/block-rendering witnesses, not evidence of manager programs, resource transfer, or full gameplay parity. `-WindowStyle Hidden` does not by itself prove that GLFW never takes OS focus; the bridge affects only its own isolated client process.
