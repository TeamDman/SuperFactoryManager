# Isolated Forge and transitional NeoForge production client bridge

This is a test-only, file-driven witness for an **unchanged** SFM production JAR. It is outside `platform/minecraft`, the source projection inputs and outputs, and the release build. It is not part of SFM. The runner uses cached Minecraft, Forge, LWJGL 3.3.1, assets, and JDK 17; it does not use Gradle or download anything. The launcher cache is read-only. The default `-MinecraftVersion 1.19.2` pins Forge 43.4.0 and asset index `1.19`. `-MinecraftVersion 1.19.4` pins Forge 45.0.9 and asset index `3`. `-MinecraftVersion 1.20` pins Forge 46.0.10 and asset index `5`. The 1.19.4 and 1.20 targets share one test-only bridge source, compiled against each target's exact cached SRG/Forge API, with separate versioned pack metadata. The transitional 1.20.1 NeoForge target is preflight-only pending an exact merged client module (see below).

Call `Run-ReleaseClientBridge.ps1` with `-SfmJar`, `-ExpectedSha256`, `-PrismRoot`, `-JavaHome`, and a **new, separate** `-RunRoot`, plus `-MinecraftVersion` for 1.19.4 or 1.20. Never pass a live game directory as the run root. The runner checks the cached launch graph before creating the run root, copies only the SFM JAR into that root, builds this tiny Forge bridge from source, starts one isolated client, and stops only the owned Java PID on timeout. For 1.20 it seeds only that scratch game's `options.txt` to skip first-run accessibility onboarding and focus pause. It retains `launch.args`, stdout/stderr, game logs, and any result or screenshot. A missing bridge result must be classified from the log stage, not treated as an SFM failure. Forge itself may make a version-check request; the runner never downloads dependencies or artifacts.

The default `-CaptureMode title` waits for 90 rendered title-screen frames so that the logo and menu widgets have appeared, captures an in-game screenshot through Minecraft's screenshot API, then exits. It does not enter a save or send user input. A title frame is a minimal visible-client startup smoke, **not** world render, GameTest, gameplay, or full release-preset parity. The direct bootstrap classpath is reconstructed from Forge installer `version.json` plus cached launcher manifests; it is not an ordinary Prism launch.

`-CaptureMode world` creates one new flat integrated-server save named from the run ID inside that run's scratch `game/saves`. The bridge refuses an existing save or a game directory other than its own scratch directory. It waits for the server and client player, places the production `sfm:manager` block on the server thread, verifies that the client received that block and that the player's ray hits it, then captures a screenshot after at least 30 `AFTER_PARTICLES` world-render events with the block still targeted. No keyboard or mouse input is sent, and no user game directory is opened. The runner requires the mode-specific result schema and a 1024×768 PNG. The screenshot must also be visually inspected: a render-stage callback alone cannot prove that the block's model was visible.

Status: separate hidden-window runs of the unchanged official 4.34.0 and fresh projected 4.34.0 production JARs both reached a fully drawn 1024×768 title screen under exact Forge 43.4.0. The bridge reported success after 90 title frames, and the runner verified each PNG and its original JAR hash. The screenshots differ in the normal rotating splash text; both display the same menu controls and four loaded mods. Offline profile-key and cached-JAR compiler-close diagnostics occurred in both runs without preventing the witness. This establishes only a bounded client startup/rendering comparison, not world or gameplay compatibility.

The same two unchanged JARs also passed separate `world` runs in new scratch roots: both produced a 1024×768 view of the manager block after server placement, client replication, ray targeting, and world rendering. Their animated manager side textures need not produce byte-identical screenshots. Both emitted the same offline profile-key diagnostic and a nonblocking `sfm:blocks/buffer` loot-table parse error. These are bounded client-world/block-rendering witnesses, not evidence of manager programs, resource transfer, or full gameplay parity. `-WindowStyle Hidden` does not by itself prove that GLFW never takes OS focus; the bridge affects only its own isolated client process.

## Exact 1.20.1 transitional NeoForge preflight — client witness blocked

The 1.20.1 release declares `net.neoforged:forge:1.20.1-47.1.65` while retaining the `net.minecraftforge` Java API and a Forge-style version identifier. The unchanged official 4.34.0 JAR SHA-256 is `34ee6eab2783b0b3a53450a6700c215e21dc653357862b24be7888e95554ef56`; the checked-in projected JAR is `6813401aeeeca8f0d1d1608e732f601b94c0eff181ba125f5bfc5dccaa6aabb9`. Both were rehashed during this preflight and were not modified. The exact installer SHA-256 is `c0056d398ccc685db87f98939ecd22d54e4a556fcb943cee00df56ed2015b6d9`.

All selected launcher-manifest inputs were cached across the isolated loader install and read-only launcher cache: 34/34 NeoForge libraries, 36/36 Minecraft libraries, 14/14 Windows LWJGL libraries, eight module-path JARs, and asset index `5`. The existing 1.20 bridge source compiled against the exact 1.20.1 SRG, Forge-universal, transitional FML 47.1.47, and eventbus 6.0.5 APIs. As in earlier runs, JBR17 printed a sandbox cache-JAR close diagnostic after producing the class file.

The exact patched client was initially absent. A scratch-only `--installClient` attempt using an explicit new target, cached libraries, an isolated launcher-profile fixture, and the exact vanilla client stopped at the installer's `DOWNLOAD_MOJMAPS` processor because network access was denied. `Build-OfflineNeoForge1201Client.ps1` instead runs only the installer's declared binarypatcher processor with its complete cached 12-JAR classpath, the cached 1.20.1 SRG client, and the installer's embedded `data/client.lzma`. It writes only to a new output root and requires the patched-client SHA-1 `97e1bb8346f4aa0e9e1bbb04e4fd170264bee508` declared by the installer. That hash matched in the retained scratch output; it does not, by itself, prove a working client launch.

Two bounded fresh-root official-title launch attempts then failed before bridge readiness. With the hash-matched patched client alone, transitional FML early display raised `NoClassDefFoundError: net.minecraft.client.gui.screens.Overlay`; the patched JAR omits that unmodified class. Adding the hash-verified vanilla SRG client as a separate game-layer JAR raised JPMS `ResolutionException` because modules `client` and `minecraft` export the same package. The separate-SRG retry was removed from the runner. `-MinecraftVersion 1.20.1` now validates exact cached inputs and deliberately stops before creating a run root until the exact merged/launcher-provided client module can be reconstructed. No 1.20.1 screenshot, candidate comparison, or world result exists. The failed scratch roots were retained, and no disk-space diagnostic occurred.
